How governor works

A short tour of governor: what it does, how an event becomes work, who owns a ticket and a pull request, and how a repo opts in. The detail lives in the code, its tests and the repo's docs.

What governor does

Governor does the work around a coding agent that a team lead would do. It watches the repos that install its GitHub App, and for each one it:

  • starts a Claude Code cloud session on each ticket that is ready, once its blockers are closed;
  • passes every comment, review, CI result and conflict on a pull request to the session that owns it, and tells that session when its change ships;
  • reviews pull requests against the repo's own checklist, and can merge the ones that pass;
  • runs recurring sessions, such as a code review every few merges;
  • archives a session once it says it is done.

It runs for one person, on their own Claude subscription and their own AWS account.

The lane and a turn

Everything governor reacts to, a GitHub webhook, the hourly schedule or a signed request from outside GitHub, becomes a fire. A small receiver checks each request and puts its fire on one queue, the lane.

  1. Something happens on GitHub, or the hour comes round.
  2. The receiver checks it and queues a fire on the lane.
  3. A starter makes sure one task is running.
  4. The task takes the fires one at a time.
  5. Each fire runs as one turn, then the next.

A turn is one fire's work. It loads the stored claude.ai login, reads the repo's config file, does what the fire asks if the repo turns that feature on, saves the login back, and archives any session that has signed off.

There is one lane and one task because there is one login. Every turn refreshes it, and each refresh replaces the old token, so two turns at once would leave one of them holding a dead login. The task stops after a quiet minute and starts again when the next fire arrives.

The fire lane animates a fire's trip from the receiver to the task, a burst of fires, and a task that fails to start.

Who owns what

Governor needs to know which session to tell about each event. A session claims a ticket or a pull request by putting its own link at the end of the body, and governor reads ownership from there.

A ticket's spec owner
The session whose link ends the ticket's body, or the person who wrote it. Only the spec owner edits the body. Anyone else who wants it changed comments on the ticket.
A ticket's builder
The session governor started to build the ticket. It hears the comments on the ticket, and when its change ships.
A pull request's owner
The session its body links, or else the live session working on its branch. Only the owner pushes to the branch. Every remark, review, CI result and conflict on the pull request goes to the owner. If the owner has been archived, governor hands the pull request to a fresh session.
The person
The repo's owner writes and approves the specs, and merges whatever the repo leaves to a person. The repo's policy decides how much that is.

A session signs off by ending its last reply with "Signing off." Governor then archives it, and the tickets it owned are free for another session to take.

How a repo opts in

  1. Install governor's GitHub App on the repo, and give the Claude GitHub App access to it too.
  2. Add a config file to the repo's GitHub folder. Each feature is one section in it, and a feature with no section is off. The starter kit has a complete file to copy.
  3. Label a ticket as ready. Governor starts a session on it and comments the session's link on the ticket.

A change to the policy is a pull request to that file. Governor reads it from the default branch on its next turn, with no deploy.
