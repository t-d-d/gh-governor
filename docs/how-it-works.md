## Why a task and a stored login

Governor starts a session with `claude --cloud "<task>"`, through `dispatch/launch-session.py`, which runs the CLI in a pseudo-terminal. The one exception is a periodic that names claude.ai connectors, which starts as a routine run ([Periodics](#periodics)).

- **A login, not a token.** Creating a cloud session sends the stored login's access token, and needs the `user:sessions:claude_code` scope and the organisation's UUID. `claude setup-token` grants inference alone, which the session-create endpoint refuses. So a headless machine can start sessions only with a copy of an interactive login, refresh token included. `scripts/mint-claude-login.mjs` makes that copy ([Minting the login](#minting-the-login)).
- **A task, not a Lambda.** The CLI refuses `--cloud` without a terminal, and the Lambda sandbox has no pseudo-terminal devices. A Fargate task has them.
- **One task at a time.** Every turn refreshes the one stored login, and a refresh rotates the refresh token. Two turns at once would leave one holding a dead login. So every fire goes through one FIFO queue, one task reads it and runs one turn at a time, and the starter never starts a second task beside a running one ([The fire lane](#the-fire-lane)).

## A turn

A turn is one fire's work (`dispatch/turn.mjs`, run by `dispatch/cli.mjs`). A task runs one turn for each fire it takes off the lane. It:

1. restores the login from Secrets Manager into the CLI's credential file;
2. reads the fire's repo's config file, or, for the bare schedule fire, lists the App's installations on listed owners and keeps the repos whose file reads valid;
3. does what the fire asks, if the repo's file turns that feature on, and otherwise logs `dispatch-refused` at info;
4. writes the login back if the CLI refreshed it;
5. archives the sessions that signed off ([Signing off](#signing-off));
6. logs its result, `dispatch-result` or `dispatch-failed`, naming the fire's message id and the turn's exit code.

A task has no timeout of its own, so the entrypoint ends a turn after eighteen minutes from its start, logs `dispatch-failed` with the reason `deadline`, and exits the task.

**Pickup.** The selection (`scripts/lib/ready-work.mjs`) takes open tickets carrying the repo's ready labels and none of its `exclude` labels or its claim label, with no open blocker, and orders them oldest first, then by number. A ticket's open blockers are the count in its dependency summary, which the issues list returns on every row. The summary counts a blocker in a repo the App cannot see, which the `blocked_by` list leaves out. A ticket with no summary is judged by its `blocked_by` list. No label ranks a ticket, and a ticket's parent issue plays no part. It skips a ticket its own `Blocked until:` line holds, as described under A ticket's own wait below. It skips a ticket whose author's `author_association` the repo's `trust.task` does not list, `OWNER`, `MEMBER` and `COLLABORATOR` by default, and logs `dispatch-pickup` at info. The older `pickup.by` is read as `trust.task`. Such a ticket takes no place under the cap. Where a person readied it, under the ready-label rule below, it gets governor's one refusal comment, saying `trust.task` refused it and that a maintainer restates the work in a ticket of their own, linking this one, or widens `task`. The comment shares the `<!-- governor:uncounted-ready -->` marker, so a ticket gets it once, and is posted whatever the switches say. A stranger's ticket its own template or a bot readied gets none. On a ticket whose author has no say in the repo, which only a wider `task` lets through, a ready label counts only when its latest `labeled` event was by a person other than the author, or by governor's own App. One the author added, as an issue template does, one a bot such as `github-actions[bot]` or another App added, and one no event names, does not count. Such a ticket takes no place under the cap, logs `dispatch-pickup` at warn with each label and who added it, never at error, so a stranger cannot page the operator, and gets one comment saying so, under a `<!-- governor:uncounted-ready -->` marker governor reads the thread for first. The comment is posted whatever the switches say. Someone with triage access who takes the labels off and adds them again starts the ticket. Who readied it is the repo's `trust.start` (`dispatch/start.mjs`), `OWNER`, `MEMBER` and `COLLABORATOR` by default, which a repo may narrow and never widen. At the default nobody is looked up, and the events are read only on a ticket whose author has no say. Once `start` is narrowed, the events are read on every ready ticket, a bot's label never counts, and governor looks up each person who added a ready label last: the repo owner's login is `OWNER`, anyone else on a user's repo is a `COLLABORATOR`, and on an org's repo the repo's outside-collaborator list tells a `COLLABORATOR` from a `MEMBER`. A ticket readied by a person outside `start` takes no place under the cap, logs `dispatch-pickup` at info, and gets the one refusal comment under the same marker, naming who readied it and who may. A lookup that fails counts the label for nothing that turn and logs at warn, with no comment, and so does a label no event names yet on a ticket whose author has a say, since its event most likely lags the label. The claim's second read checks every rule again. Every served repo's tickets go into one queue, under the stack's `DispatchCap` (two by default). For each ticket governor adds the claim label, takes off `claimRemoves`, starts the session, and comments a `<!-- governor:dispatched <session URL> -->` marker with the session's link, which names the ticket's builder. The claim label, not the marker's age, keeps the ticket out of the selection while it is built: a ticket whose claim a person removes is selected again. If the launch started nothing, it puts the labels back. A schedule fire starts no launch past seven minutes into the turn, and logs the rest as `undispatched` for the next fire.

**What a pickup session does first.** Governor's default `pickup` prompt tells the session to read its ticket against the code before it builds. If the code already does what the ticket asks, or the work is far larger than the ticket reads, the session comments on the ticket saying which and what it found, and stops without building. The ticket keeps its claim label, so pickup does not start it again, and a person decides what happens to it. No pull request will close to ask such a session to sign off, so where the repo's file turns `signOff` on, the prompt asks it to sign off once it stops, in the words of the repo's `signOff` prompt where it sets one. With the switch off, the prompt carries no ask. A repo that sets its own `pickup` prompt gets that text unchanged, with neither the check nor the ask.

**A ticket's own wait.** A ticket whose body's first non-empty line starts `Blocked until:`, in any case, waits. The value is a date, `YYYY-MM-DD`, and the wait ends at 00:00 UTC on that date. Text after the date, past a space, is a reason and changes nothing: `Blocked until: 2026-11-05 for a few days of log lines`. The reader that builds each ticket's row carries what the line says (`waitOf`, `scripts/lib/ready-work.mjs`), and the shared readiness rule holds the ticket while the date is still to come (`isWaiting`). The selection, the claim's second read and the `unblocked` row all apply it, in every served repo, with no switch: a line a person wrote is never silently ignored. A ticket that gains the line after the plan is made is skipped at its claim, logged as `dispatch-claim` with `no longer ready to claim`. In the `unblocked` row the line holds only a ticket whose labels read ready or not ready, which reads as blocked, so a blocker's close starts nothing for it. A claimed ticket's session is already running, so it still hears its blocker close, and an excluded ticket still reads excluded. A line that starts `Blocked until:` but holds no date governor can read, such as `2026-13-01` or `next week`, holds the ticket too. Governor logs `dispatch-wait-unreadable` at warn and comments once on the ticket that it cannot read the date (`dispatch/waits.mjs`). The comment carries a `<!-- governor:wait-unreadable -->` marker, and governor reads the ticket's thread for it before it writes another, so a later sweep does not repeat it. Deleting the line frees the ticket at the next sweep; changing the date moves the wait.

**A relative wait.** The value may instead be `<N> days after #<issue> closes`, or `<owner>/<repo>#<issue>` for another repo's issue, with `N` a whole number from 1 to 36500, a hundred years, and any reason after `closes`. A larger count is unreadable. The named issue must be a declared blocker of the ticket. While it is open, the dependency hold keeps the ticket out. The line holds it too, in every repo, until governor has rewritten it into a date (`dispatch/waits.mjs`).

- **The close.** The closing turn reads the issue's `closed_at` and gives it to each `unblocked` fire. A ticket of its own repo whose line waits on the close is queued even where the file turns `pickup` and `unblocked` both off, and its turn reads the ticket once before it refuses. Before it picks a row, the ticket's turn settles a line that waits on this close. A completed close, or one GitHub gives no reason for, rewrites the line to `Blocked until: <date> (<N> days after #<issue> closed)`, keeping any reason after it. The date is the first day whose 00:00 UTC is at least `N` days after the close. Governor reads the body just before it writes and replaces only that line, so a person's edit elsewhere stays. The edit's `edited` delivery reaches the `wait` turn like any dated line. Any other close leaves the line, and comments once in the words of the repo's `unblockedNotPlanned` prompt, saying the ticket stays held and that a date or deleting the line frees it. That comment carries a `<!-- governor:wait-not-planned #<issue> -->` marker and replaces the not-planned row's comment. Either way, a ticket ready or not ready by its labels reads as held, and nothing starts. A claimed or excluded ticket is not held, and takes its own row: a claimed ticket's session hears the close, in the not-planned row's words where the close was not planned, and the ticket gets no second comment. On such a ticket the comment says the line waits on a close that does not give it a date, not that the line holds the ticket.
- **The `wait` turn**, with `waits` on, keeps no item for a relative line and drops one that stands. On a ticket ready or not ready, it links a same-repo issue the line names as a blocker where it is not linked, and settles the line as at a close where that issue has already closed. It does not read another repo's issue, which a person must link. A pull request, or the ticket itself, cannot be a blocker, so a line naming one gets the one comment the sweep gives, under `<!-- governor:wait-relative #<issue> -->`. The schedule fire drops an item whose ticket's line became relative.
- **The sweep.** The bare schedule fire meets a ready ticket whose relative line no open blocker holds: the issue was never linked, or governor missed its close. It settles a same-repo line from that issue's close, and otherwise comments once, under `<!-- governor:wait-relative #<issue> -->`, saying to link the issue as a blocker or write a date. A repaired close long past can give a date that has passed, which frees the ticket with no wait-ended comment.

**When a wait ends.** With a repo's `waits` switch on, governor acts when a ticket's wait is over (`dispatch/waits.mjs`).

- **The fire.** An issue opened or reopened with the line, or edited where its new or old body holds it, queues a `wait` fire naming the issue. The receiver judges this from the payload, and drops the fire where the repo's hook-table item says `waits` is off. An edit that leaves the body alone queues none.
- **The item.** The `wait` turn reads the ticket and keeps one item for it in the state table, `wait#<repo>` / `<issue>`, holding the date while it is still to come. A date that has passed keeps an item that stands, at that date, so the schedule fire still acts on it; with no item it puts none. No line or a closed ticket deletes the item. An unreadable line deletes it, and gets the hold's comment on a ticket that is ready or not ready by its labels: a claimed ticket is someone's work, and is not told it is held. The item only tells governor when to look: the ticket's line stays the record people read. Each write goes only over the item the turn read, and the turn logs `dispatch-wait`.
- **The schedule fire.** It reads the items of each repo with `waits` on, and reads again each ticket whose date has passed. A ticket closed, deleted, moved to another repo, or without its line loses its item. One whose line now holds a later date keeps its item, rewritten to that date, and is not released. A ticket that is ready, claimed, excluded or still blocked loses its item and gets nothing: pickup, or its blocker's close, takes it on. A ticket that is not ready gets one comment saying the wait ended, under a `<!-- governor:wait-ended <date> -->` marker governor reads the thread for first, so it never repeats. With `unblocked` on too, it gets its spec work, unless governor took its ready labels off on a not-planned close and nobody has answered since (below). Such a ticket still gets the comment, and its item goes. Where the ticket's body names a session, its owner, governor messages that session with the wait's facts and the `waitEndedOwnerSpec` ask, to rewrite the spec in its own body, as a blocker's close does ([The ticket's owner](#a-turn)). If the owner is archived, a spec session starts in its place. Where the body names none, the ticket gets a spec session on the repo's `waitEndedSpec` prompt, unclaimed, as a blocker's close starts one. Either way governor writes the new spec session's link into the ticket's body as its owner link, and posts no dispatch marker. A ticket whose author the repo's `trust.auto` does not let in, `OWNER`, `MEMBER` and `COLLABORATOR` by default, gets the comment but no spec work, and its item goes, logged on `dispatch-wait` at info. At most `DispatchCap` such sessions start a fire, apart from pickup's, and they do not count as pickup's starts; one past the cap keeps its item. An owner is messaged whatever the cap, and its ticket's item goes once it took the message. A spec session's item goes once it has started; a launch that starts nothing, an archived owner past the cap, or a `DispatchCap` of 0, leaves it for the next fire, which does not comment again. An owner's message takes the spec session's place in the fire's launches, so the launch window and a repo skip hold it as they hold a launch. Nothing is posted on the ticket of an owner that took the message. If a spec session started and its item could not be deleted, the next fire finds that session as the ticket's owner, through the link governor wrote, messages it again and deletes the item: it never starts a second spec session. A ticket or comment that fails logs `dispatch-wait-unhandled` at error, keeps its item, and the turn exits 1.
- **The wait ticket.** A file with `waits` on may name one, `"waits": { "issue": <number> }`, and governor then shows each wait in its ticket's sidebar by linking the ticket as blocked by it. Without the section, governor links nothing. The `wait` turn links a ticket whose date is still to come, once its item is written, unless it is linked already; a link that fails logs `dispatch-wait-link` at error and changes nothing else, since the line holds the ticket. Any other line, or a closed ticket, takes the link off; where the line was deleted, before the item goes, so a removal that fails fails the turn and leaves the item for the schedule fire. The schedule fire reads the ended waits before its sweep reads the backlog, and takes each ended ticket's link off first, because pickup holds a ticket while its dependency summary counts an open blocker and the wait ticket never closes. A removal that fails keeps the item for the next fire. A summary a moment slow to catch up means a ready ticket is picked up at the next sweep instead, and a link just removed does not count as a blocker when the fire judges a ticket that is not ready. A ticket linked to the wait ticket with no line where no item stood, such as one linked by hand, gets one comment under a `<!-- governor:wait-unlined -->` marker, and keeps its link: the `wait` turn finds it when its body is edited, and the schedule fire finds the rest from the wait ticket's `blocking` list. Once told, the ticket is recorded in the state table, `unlined#<repo>` / `<issue>`, for a month, and a schedule fire that finds it there with no line in its row reads neither the ticket nor its thread. A lost record costs one more read of the ticket and its thread, which finds the marker and records it again. The same list gives the schedule fire any ticket with no item whose line has passed or cannot be read, linked by a turn that then failed to take the link off, and its link comes off before the sweep. GitHub lets one issue block at most 50; a link refused with a 422 whose text names that limit, or while the wait ticket already blocks 50, gets one comment on the ticket under `<!-- governor:wait-full -->`, logged at warn, and the line still holds it. A closed wait ticket gets no new links, logged at warn, and still loses the links of waits that end.
- **The prompt line.** Every launch in a repo with `waits` on ends, after the line on signing posts, with a line saying that a ticket waits until a date when its body starts with `Blocked until: YYYY-MM-DD`.
- **Lost deliveries.** A lost `opened`, `reopened` or `edited` delivery leaves its ticket without an item, so a ticket that is not ready gets no wait-ended comment or spec session. A ready ticket loses nothing, since pickup reads its line on every sweep.

**Which fire picks up what.** A ready label added by a person queues a fire for that one issue. The receiver knows each repo's ready labels from the repo's item in the hook table ([The webhook](#the-webhook)). An issue closing frees what it directly blocked, in every served repo ([A blocker's close](#a-turn)): a close never runs the whole selection, so one finished session cannot start a cascade. The hourly fire runs the whole selection over every served repo whose sweep is due. Only that sweep writes pickup's heartbeat line ([The heartbeat](#the-heartbeat)).

A fire that names one issue, a label's fire or an `unblocked` fire for a ready ticket, reads that issue itself and judges it by that read, not by the ready list. GitHub's filtered issue list shows a label change about four seconds after it, and the fire's turn can run a second after the label, while a read of the single issue shows the change at once. A label's fire whose read finds the issue not ready, claimed or blocked starts nothing, and logs `dispatch-pickup` with the issue and what its read saw: its labels and its open blocker count. An `unblocked` fire logs `dispatch-unblocked` instead. A read that finds the issue gone, or that GitHub redirects to an issue it moved to another repo, starts nothing.

**A blocker's close.** An issue can block a ticket in another repo, so a close is handled in each blocked ticket's own repo (`dispatch/unblocked.mjs`). The closing turn reads the closed issue's blocked list and the PR whose merge closed it, if one did. It queues one `unblocked` fire for each open blocked ticket in a repo whose owner is on the owner list, carrying the ticket, the blocker's repo, number, title and close reason, and the PR's number, title and link. Each fire's deduplication id is built from the closed issue and the ticket, so a retried close queues nothing twice. No cap applies: each fire starts at most one session and queues nothing. The closing turn calls GitHub only under the closed issue's repo, and starts nothing.

Each `unblocked` fire runs in the ticket's repo's own turn, under that repo's config. It reads the ticket and its blockers there and acts on the first row that fits. The turn runs seconds after the close, and a read then may still count the closed blocker as open, so an open ticket that reads blocked is read again, up to four reads three seconds apart. The `dispatch-unblocked` log line carries each read's labels and open blocker count.

A not-ready ticket's spec work, in the two rows above, starts with nobody choosing the ticket, so it goes only to a ticket whose author the repo's `trust.auto` lets in (`dispatch/trust.mjs`), `OWNER`, `MEMBER` and `COLLABORATOR` by default. Anyone may open an issue on a public repo and link it as blocked by a real ticket. For any other author nothing starts and nothing is sent, and the turn logs `dispatch-unblocked` at info, naming the author's association.

**The ticket's owner.** Governor reads an issue's owner from its body: the last session link under the Claude Code footer, or a link alone on the last line (`sessionNamedIn`, `dispatch/webhook/subscribe.mjs`). Claude Code ends any body a session writes with that session's link, so a session that rewrites a ticket's body takes the ticket over, and the filer hears nothing more of it. So governor never asks a session that does not own a ticket to edit its body. A not-ready ticket's spec work goes to its owner first. The spec session is the message's fallback (`deliver`, `dispatch/deliveries.mjs`): it starts only when the owner refuses as archived, and it counts against `DispatchCap` as a spec session does. With a `DispatchCap` of 0 the owner is still messaged, and nothing starts in its place. A send that fails for another reason, or a fallback that starts nothing, exits 1. 

**The ticket's spec session.** The body's owner link is the ticket's spec session, and no timer stands in for it. Whenever governor starts a spec session for a ticket, as the owner's fallback or because the body names none, it writes the new session's link into the body as the owner link at once (`nameSpecSession`, `dispatch/deliveries.mjs`), in place of an archived owner's, as it does for a PR handed to a new session. So a second close, however soon, reaches the session the body now names, and starts no other. A spec session leaves no dispatch marker: a marker names a builder that is not the owner, and only a pickup launch posts one. A ticket the spec session or a person readies is picked up by its label's own fire. A write that fails, or a launch that printed no session link, logs `dispatch-spec-owner` at error, since the ticket's next spec work then starts another session.

A ready ticket's pickup session comments instead of editing an owned body, so the owner hears the comment, as it hears every comment on its issue, and updates its own spec.

The label removal sits under `pickup` because pickup is what could start the ticket, so a repo with `pickup` on is held whatever `unblocked` says. The sentence about the labels is fixed text, not part of the `unblockedNotPlanned` prompt, so a repo that replaces the prompt still says it.

A comment that says a ready label came off carries a `<!-- governor:unreadied -->` marker, on a retried fire too. When another blocker later closes and the ticket reads as not ready, the turn reads the ticket's thread first. If governor's newest comment with that marker has no comment after it from anyone but governor, it starts no spec session and logs `dispatch-unblocked` saying so. The schedule fire reads the same hold when the ticket's wait ends, and logs it on `dispatch-wait`. A person's comment after it is an answer, and the next close starts the session as before. Putting the ready labels back makes the ticket ready, and pickup takes it on. A thread that cannot be read fails the turn, which logs `dispatch-failed`. The fire is not retried, so the hold is read again only on the ticket's next fire: another blocker's close, or the schedule fire when its wait ends.

The closing turn cannot read another repo's switches, so it queues the fire anyway, and the ticket's turn ends when its switch is off. For its own repo, it skips the fire when the file turns neither `pickup` nor `unblocked` on, unless the ticket's line waits a number of days after this close. With `unblocked` on and `pickup` off, a spec session can still claim a ticket and build it; one that only marks it ready waits for nothing to start it.

**Pickup's sweep interval.** A repo's file may set `"pickup": { "sweepHours": <n> }`, whole hours of at least one; unset is one, so the repo is swept at every fire (`dispatch/pickup.mjs`). Governor keeps each repo's last sweep in the state table, under `pickup#<repo>` / `sweep`. The hourly fire sweeps a repo once its interval has passed since that time, and records the sweep after its launches, unless the repo's backlog could not be read, every claim or launch failed, a failed launch or the launch window left some of its planned tickets, or `DispatchCap` cut a ticket the fire would otherwise have started, so the next fire tries again. The cap limits load; it does not set how often a repo is swept. The fire's clock is the stack's `ScheduleExpression`, which the file cannot see, so the turn applies the floor: the first fire at or after the interval sweeps, and an interval of one tick or less sweeps at every fire, however late the last sweep's turn ran. The record holds the time the turn ran, which can lag its fire when the fire waited behind another turn, so a sweep up to half an hour short of its interval still counts as due. A repo not yet due logs `dispatch-pickup` with outcome `not due`. A missing record, for a new repo or a lost item, means sweep now. A record that cannot be read refuses the repo's sweep for the turn (`dispatch-pickup-unread`, and the turn exits 1), and one that cannot be written logs `dispatch-pickup-unrecorded` and exits 1. A label or a blocker's close picks up at once whatever the interval. A new ready label added to a ticket before the repo's next turn has written it to the hook table waits for the sweep.

**Periodics.** The hourly fire also starts each periodic that is due, ahead of the tickets. A merge, an issue opened or an issue closed can bring one due too ([Periodics](#periodics)).

**Each repo on its own.** Each served repo gets its own installation token, workspace and cloud environment. A repo whose `claude --cloud` launch fails is skipped for the rest of the fire (`dispatch-repo-skipped`), and the other repos still go. A periodic whose routine the routines API refused stops only that periodic (`dispatch-routine-refused`).

## Triggers

The receiver (`dispatch/webhook/route.mjs`, `mention.mjs`, `subscribe.mjs`, `hook.mjs`) queues a fire for each of these, unless the repo's hook-table item says the fire's switch is off ([The webhook](#the-webhook)). The task checks the repo's switch again before acting.

| Event | Condition | What happens | Switch |
|---|---|---|---|
| Issue labelled | A ready label, added by a person | That issue is picked up, if the selection would take it | `pickup` |
| Issue closed | It blocked open tickets, in any listed owner's repo | One `unblocked` fire per ticket, which its own repo's turn acts on ([A blocker's close](#a-turn)) | `pickup`, `unblocked`, in the ticket's repo |
| Hourly schedule | Always; pickup once the repo's sweep interval has passed | Every served repo: pickup, heartbeat, sign-off sweep | `pickup`, `heartbeat`, `signOff` |
| Hourly schedule | A periodic's day limit has passed since its last fire, or one of its counts is reached, and its last run's session is not open | One session on the periodic's prompt, or none and a "nothing to do" record when its counts counted nothing | `periodics` |
| PR merged into the default branch, issue opened, issue closed | A periodic counts that kind, and its count since its last fire is reached, and its last run's session is not open | One session on the periodic's prompt, after the carrying turn's own work | `periodics` |
| Comment, issue or review with `@claude` | By an owner, member or collaborator; no session owns the PR | One session, pointed at the remark | `summons` |
| Comment, review, push, merge or close on a PR | The PR names a session, or a local session holds its branch | A message into that session | `prMessages` |
| Comment, label, close or reopen on an issue | The issue's filer, or a subscribed session | A message into each | `subscribeMessages` |
| Any event on a PR or issue | A `governor:subscribe` line names a session for that event | A message into it | `subscribeMessages` |
| PR merged | Other open PRs into the default branch are now conflicted | A message to each one's session | `conflicts` |
| CI run on the default branch went red | Started by a push; the run before it was green | Messages to the suspect merges' sessions, or one fresh session | `ciMessages` |
| Shipping job on the default branch succeeded | Its name ends `· deployed: <target>` | Messages to the sessions of the merges it shipped; labels their tickets | `deployMessages`, `deployedLabels` |
| Deploy run on the default branch went red | Its workflow marks a shipping job | Messages, or one fresh session for a `triage` target | `deployMessages` |
| Scheduled run on the default branch went red | First attempt | One fresh session on the run | `redScheduledRun` |
| Dispatched run on another branch finished | Any outcome | A message to the session that wrote its commit | `branchRunMessages` |
| PR opened, ready, pushed to, or its body or base edited | Not a draft | The PR review | `prReview` |
| Check run completed, status ended, or workflow run finished, off the default branch | Not governor's own check; a status that is not pending | The PR review of each open PR at that commit | `prReview` |
| Issue opened, reopened, or its body edited | Not a bot's edit | Each ticket review whose selector the issue meets and whose marker its body has moved past, and its conclusion's labels | `ticketReviews` |
| A signed `POST /hooks/<owner>/<repo>/<hook>` | The signature matches the hook's key, its time no more than 30 seconds ahead of the receiver's clock or 4 minutes 10 seconds behind it; the file lists the hook at that key version | One session on the hook's prompt, with the caller's text below it, or a message into the hook's last session while it is open | `hooks` |

A mention starts a session only from someone with a say in the repo. A bot cannot, and neither can a session, whose posts end in the Claude Code footer. On a PR a session owns, a mention starts nobody: the owner is messaged instead. The receiver drops a mention from anyone else, silently. The summons fire names the issue or PR it is on and its author's `author_association`, `BOT` for a bot and none for governor's own App, and the task starts the session only where the repo's `trust.task` lets that author in (`dispatch/dispatch-fire.mjs`). A refused summons starts nothing, logs `dispatch-launch` at info, and gets governor's one refusal comment, under the `<!-- governor:uncounted-ready -->` marker, so a second summons there gets no second comment. The receiver does not read `trust.task`: every summons it refuses needs that comment, and the writer check already drops the rest. The fire also names who set it going, judged by the repo's `trust.start`: the writer's `author_association`, which the receiver has held to the three, or, for an issue assigned to `claude`, the assigner's login, which the task looks up only where `start` is narrowed, as pickup looks up who added a ready label. A summons from someone outside `start` starts nothing, logs `dispatch-launch` at info, and gets the same one refusal comment. An assigner the lookup cannot place starts nothing that turn, logged at warn.

Everything governor sends into a session starts with one line that names where its text comes from. A message relaying GitHub activity starts `[governor] Automated message from the governor dispatcher, relaying GitHub activity; …`, so the session knows it is reading a report and weighs each quoted remark by who wrote it. A hook's fire into its open session starts with a line naming the hook instead, which says the text is its caller's data ([Hooks](#hooks)). A prompt that a person or the schedule starts a session on carries no such line.

Every message ends with the session's standing: the other open PRs and issues that name it, or "No other open PR or issue names this session". When nothing else is open, an issue's close, a PR closed unmerged, or a green deploy also asks the session to sign off, unless it knows a reason not to. A merge does not ask, because CI and the deploy are still to come.

## Who a PR or issue belongs to

**A PR a cloud session wrote** names it: the last `claude.ai/code/session_…` link under the Claude Code footer in its body. Every comment, review comment and review on it goes to that session, mention or not, review bots included. What does not reach it: its own signed posts, a comment by an author the repo's `trust.relay` does not let in, and a review with neither text nor a verdict.

**Whose text reaches a session** is the repo's `trust.relay` (`dispatch/trust.mjs`): `OWNER`, `MEMBER`, `COLLABORATOR` and `BOT` by default, where `BOT` is any account GitHub marks as a bot. A comment or review is judged by its author. A session link or a `governor:subscribe` line in an issue's or PR's body counts only where the body's author is let in (`relayedBody`, `dispatch/webhook/subscribe.mjs`), wherever governor reads it: the receiver's routing, a message to a PR's owner, the owner found by head branch, CI and deploy messages, and a session's standing line. So a stranger who copies a session link into an issue routes nothing to that session. An event that carries no text, a label, a close, a reopen or a push, is judged by the author of the issue or PR it is on, since GitHub's payload carries no association for its sender. Governor's own App is never judged. Each refusal is logged at info and pages nobody. The receiver judges by the repo's hook-table item ([The webhook](#the-webhook)), and the task judges each message again from the file before it sends.

**A session's own post** is skipped only where the session signed it, with its link under the Claude Code footer or alone on the line just above it. The footer Claude Code puts on a comment names no session, so every session governor starts is told in its opening prompt to sign its posts. A post with the footer and no link may be any session's. It reaches the owner and every subscriber. The message tells each one that if it wrote the post, it should post nothing about it and sign its posts from then on. Skipping the owner instead would lose a remark from another session, such as a reviewer's, and an owner that nothing wakes leaves its PR idle.

**When the owner is archived**, the message is refused, and governor starts a fresh session on the same text, told to take the PR over. It rewrites the PR body's session link to the fresh session, so later remarks go straight to it, and posts no comment on the PR: the body's link is the one record of a PR's session. A remark queued before the rewrite, such as the rest of a review's inline comments, still names the archived owner. When that owner refuses, governor reads the body again and sends the remark to the session it names now, rather than starting another on the same branch. A rewrite GitHub refuses, or a launch that printed no session link, logs `dispatch-relink` at error and the turn exits 1. The body then still names the archived owner, so the next remark takes the PR over again.

Only one answer counts as a refusal: `cloud session <id> is archived`. Any other failure says nothing about the session, which may be live. Governor sends once more five seconds later; if that fails too, it starts no fallback, drops nothing, and fails the turn.

**A PR raised from a local session** (the CLI, or the desktop app with Remote Control on) names no session. Governor reads the PR's head branch and asks the sessions API for the most recently updated local session holding that branch, not archived. A cloud session on the branch does not count: it checked the branch out to review or fix it. With none found, nobody is told.

**An issue a session filed** names it the same way, and the filer hears every event on it but labels: comments, the close, and a `deployed:` label only if it subscribed to `deploys`. A session link that is the whole of the body's last line also counts, since some tools strip the footer from an issue body.

**Any other session** subscribes to a PR or issue it is party to by adding one line to its body, and unsubscribes by removing it:

```
<!-- governor:subscribe https://claude.ai/code/session_… events=comments,reviews,pushes,close -->
```

`events` is a closed list. Absent means all.

| Event | What it covers |
|---|---|
| `comments` | Issue comments and review comments |
| `reviews` | Submitted reviews |
| `pushes` | A push to the PR |
| `close` | A PR closed, merged or not; an issue closed or reopened |
| `labels` | An issue labelled or unlabelled, except a `deployed:` label added |
| `ci` | A red CI run on the default branch that this PR may have caused |
| `deploys` | A shipping job or a red deploy that shipped this PR; on an issue, a `deployed:` label added |

A PR's owner is implicitly subscribed to everything but `labels`; an issue's filer to everything but `labels` and `deploys`. A subscriber that refuses loses its `governor:subscribe` line (`dispatch-unsubscribe`), since nothing takes its place. An owner that refuses keeps its link, an issue's as a PR's, so a ticket always names the last session that owned it. Each later event on that ticket tries the archived owner once more, and the refusal logs `dispatch-message` at info. Spec work to it starts a replacement, which takes the owner link ([The ticket's spec session](#a-turn)). Nobody hears of its own signed post: the receiver skips the session whose link sits under the Claude Code footer or alone on the line above it. A post with the footer and no link reaches every subscriber, told it may be its own (above). A push names its commit, and the session its `Claude-Session` trailer names is skipped.

## Signing off

A session cannot archive itself unattended: the archive tool reaches a session only on a turn the operator typed. So a finished session signs off in words, by making `Signing off.` the last line of its reply, and every turn but a probe sweeps (`sweepSignoffs`, `scripts/lib/session-signoff.mjs`, [constraints/session-signoff.md](constraints/session-signoff.md)).

The sweep and the ask to sign off are the `signOff` switch's, off unless the repo's file turns it on. With it off, governor archives none of the repo's sessions, and its messages never ask a session to sign off.

The candidates are the login's sessions that are idle, not archived, and name a served repo whose file turns `signOff` on. The sweep reads them most recently updated first, for up to a minute, and leaves the rest for the next turn. For each, it reads the session's newest events and takes the reply: the newest `result` text, or the nearest assistant text before it. A reply whose last line starts `Signing off` signs the session off. The sweep reads the session again, so a prompt that landed meanwhile keeps it open, and archives it. Each candidate logs one `dispatch-signoff` line with the decision, never the reply's text.

A session's sign-off is usually its reply to a message the same turn sent. So a turn that messaged sessions, with nothing else queued, re-reads those sessions every 15 seconds for up to three minutes, until each has replied or a fire is waiting (`dispatch-signoff-wait`).

The sessions API is not a documented one. If it changes, the sweep logs the refusal and archives nothing, and the sessions stay open until archived by hand.

A local session with Remote Control on is listed and swept like a cloud one. The archive ends its Remote Control link, but the desktop app keeps its window. A served repo that wants local sessions to close themselves can add a Stop hook that asks the session to call the desktop app's archive tool on its sign-off turn.

## CI and deploys

**CI.** The repo's `workflows.ci` names its CI workflow. Only a run started by a push counts: a run dispatched by hand tested no merge. A red run whose previous run was green blames the merges between them.

- One suspect PR: its session is told the run, the failed jobs and the PR, and asked to fix it on a new branch if its change caused it. If that session is archived, a fresh session starts on the same text. It raises a PR of its own, and nothing is posted on the suspect PR, whose owner does not change.
- Several suspects: none of their sessions is told. One fresh session gets the run and the suspects, finds the culprit, and fixes it.
- One suspect Dependabot opened: one fresh session, to fix forward or revert the bump.

A red run after a red run tells nobody: its breakers were already told.

**Deploy targets.** A shipping job's name ends `· deployed: <target>` (a middle dot, one space each side), optionally with `at <sha>`, the commit it built, before it. The workflow file declares a top-level `TICKET_LABEL_PATHS`: `all`, `trigger` (the workflow's own push paths), or globs. Governor reads both at the run's commit; no list of workflow names picks them.

- A green shipping job tells each PR it shipped that its change is on the target, naming the job and the target's tag from `workflows.tags`. With `deployedLabels` on, it labels each ticket those PRs closed `deployed: <target>`.
- A red run of a deploy a merge starts (a workflow on `push` or `workflow_run`) tells each PR it shipped that the deploy failed, and asks for a fix only if its change caused it.
- A red run of a `triage` target starts one fresh session over every merge it shipped instead, since those sessions have usually signed off.
- A red release dispatched by hand tells nobody: whoever dispatched it is watching it.

A session hears of a run once, however many of its PRs the run covers.

**Cursors.** A job or run covers every PR merged since its baseline. Each label has a cursor in the state table: the newest run a turn planned. A turn moves it forward after its sends, and never back. A refused turn leaves it, so the next job's range tells and labels the refused job's merges too. A note the turn could not send holds the cursor, and the turn records which sessions it did tell, so the next job tells only the rest. A session that fails three turns running is given up on.

GitHub's runs list can lag. A list missing the run is read again after 10, 30, 60 and 90 seconds; still missing, the turn tells nobody and logs `dispatch-stale-runs`, which raises an alarm.

## Conflicts after a merge

GitHub has no event for a PR that a merge leaves conflicted. So a PR merged into the default branch queues a `conflicts` fire (`dispatch/conflicts.mjs`), whose turn reads each open, non-draft PR's `mergeable`. A `null` starts GitHub's computation, so those are read again three seconds later, up to five reads. A PR still `null` is never taken for a conflict.

Each conflicted PR's owner session is told the PR, the merge that moved the base and the base's new commit, and asked to merge the base in, resolve, check and push. An archived owner gets a fresh session told to take the PR over. That session starts on the PR's head branch and pushes there, so it opens no second PR, and the PR body's session link is rewritten to it, as for a remark. A PR from a fork has no head branch in the repo, so its session starts from the default branch. Nothing is posted on the PR. Each PR is told of each merge once, recorded in the state table. A PR with no owner session is told nothing. A PR whose author the repo's `trust.auto` does not let in, `OWNER`, `MEMBER` and `COLLABORATOR` by default, is skipped: a person tells its author.

## The PR review

The review runs in each served repo whose file turns `prReview` on, from that repo's `review` section ([constraints/dispatcher-review.md](constraints/dispatcher-review.md)). The image carries no repo's checklist: each review reads the repo's own, from its default branch. The review turn (`dispatch/review.mjs`) reads the PR, the tickets its body closes and the last review marker, then runs `claude -p` under the stored login with governor's fixed frame, the repo's checklist and a suffix naming what the code decided in place of Claude Code's system prompt (`--system-prompt-file`), the PR's facts on stdin, no tools, and the answer held to a JSON schema. The review starts no session.

**Decided in code.** Three tests are decided before the model is asked, and a PR failing one is commented on without a model run:

- Test 1, the tickets: each ticket the PR closes is open, meets `review.tickets`, and carries the claim label. A ticket not yet claimed gets a comment the author session hears. A PR closes tickets in its own repo only: a body that closes another repo's issue, by `owner/repo#N` or by its URL, fails for an edit, as does a closing reference below the body's top `Closes #N` lines. Work spanning repos links the tickets with `blocked by`: the other repo's ticket is blocked by an issue here, a PR here closes that issue, and its close unblocks the other ticket.
- Test 7, the human-only list: no changed path, or path a rename left, matches `review.humanOnly`, unless every ticket carries one of the entry's `unless` labels. A modified file matching `review.quote` goes to the model instead, quoted whole at the merge base and at the head. A `decides` ticket's first line, `Constraint now lives at <path>, …`, passes the quoted files it names.
- Test 8, required checks and CI: no status check the default branch requires, and none the repo's `review.requireChecks` lists, is red on the head. A listed check counts as a required one does, so a repo whose plan cannot require checks can still name them; a name on both counts once. A listed entry that names its App is met only by that App's check run of the name, so a job of the same name in a PR's own workflow cannot stand in for it. Where the repo's file names `workflows.ci`, the latest run of that workflow at the head counts too, so a repo whose plan cannot require a check still holds a pass for red CI. A red CI run fails test 8 for the author session's push, naming the workflow file. A green or skipped run passes. A check or CI run still going, or a CI run not yet started at the head, skips the review. A check run completing or a status ending at the head queues a new one, and so does the CI run being marked complete, which can come minutes after its last check. A PR from a fork is read again the same way, since the new review is queued for the commit, not the PR. One gap remains. A check run's event names no head repository, so a check that ends on a branch named like the default branch queues nothing, in case it is the repo's own. A fork PR opened from the fork's own default branch is therefore not read again when a check from an App other than Actions ends. Its Actions runs still queue a review when they finish, since a workflow run names its head repository, and a push or an edit to the description reviews it again. Runs of any other workflow, and CI runs at other commits, do not count. A CI workflow with a `paths` filter has no run at the head of a PR it skips, so that PR waits until a push starts one, or a person merges it, as it would on a required check. A repo whose CI workflow runs only after the merge sets `review.waitForCi` to `false`, and the review then reads no CI runs, only the checks. The review's own `governor` check is left out, so a repo that requires it never waits on it.

So a checklist numbers its own tests 2 to 6. Code also fails tests 5 and 6 when the PR body's Verification table or Left for later names a ticket that is closed or does not exist; the rest of those tests are the model's.

**Pass.** Governor waits for GitHub to compute the PR's mergeable state, merges with a merge commit pinned to the head it reviewed, and comments `Passes the PR review: <reason>.` With `review.merge` false, it merges nothing, and the comment ends `The repo's owner merges it.` Governor approves nothing. A conflict is a comment telling the author session to merge the base in.

**A pass reused at a new head.** A push that only merges the base branch in puts the model the question it already answered. The model reads the checklist with the suffix naming what the code decided, and answers under a schema. Its prompt holds the PR's title and body, the tickets the PR closes with their text and labels, one line per changed file with its status, and each quoted file's text at the merge base and the head. It holds no other file's contents and no patch. Where the model was asked, the marker carries a sha256 digest of all of that, with the commits left out. At a new head, where the last review was a pass, a pass the owner merges or a conflict, and the digest is the same, governor posts the pass again without a model run. Its comment adds `Reuses the answer given at <sha>: nothing the model reads has changed since.`, naming the head the model answered at, and its check and marker name the new head. The tests decided in code run first, as for any review, so a red required check, a conflict or a human-only path still fails. A fail is never reused, nor is a pass whose marker carries no digest: one from before the digest, or one decided in code. A body edit, a changed file list, a closing ticket's text or labels, or a quoted file's text at either end changes the digest, and the model is asked. The `dispatch-review` line of a reused pass has no `usage`.

**Fail.** A comment naming the first failed test: `Waits for a description edit: …` where an edit to the PR body would pass it, or `Waits for a person: …` where none can. A fail on the same test as the last review edits that comment in place rather than posting again.

**The check.** Each review that answers also posts a check run named `governor` on the head it read, titled with the comment's first sentence and carrying the comment as its summary. A ruleset can require it, with governor's App as its source, so a PR cannot merge while its session still owes a fix.

| The review | Check |
|---|---|
| A required check, a listed one, or the CI run at the head, has not finished | `in_progress` |
| Passes | `success` |
| Passes, but conflicts with the base | `failure` |
| Waits for a description edit, a claim or a push, with or without a person after it | `failure` |
| Waits for a person | `neutral` |
| Skips a PR by an author the repo's `trust.review` leaves out | `neutral`, saying a person merges it |
| Does not finish: the login's usage limit stops it, or it fails | `failure`, saying it did not run and why, and that a push or an edit runs it again |

GitHub counts `neutral` as passing a required check, so only a PR handed to a person gets it. Every other skip posts no check. A pass's check goes before its merge, and a fail's before its comment. The check needs the App's Checks write. An installation that has not accepted it answers 403, which the review logs as `check` on its `dispatch-review` line and passes over. Governor reads a check run's end only from other Apps, so its own check ending queues nothing and its Re-run button does nothing. A push or an edit to the description reviews again.

**Who hears it.** Every comment ends with `<!-- governor:pr-review <head sha> <body sha256> -->`, and where the model was asked or its pass reused, ` <read sha256>` after the body's digest. The receiver takes a comment for the review's only when it carries that marker and the stack's own App posted it. The owner session is messaged with every new comment, the marker taken out. Only a comment that asks something of it carries the fallback that hands a gone session's PR to a fresh one: an edit, a ticket to claim, a red required check or a conflict. A pass, or a fail only a person can clear, would give a fresh session nothing to do. Subscribers are not messaged.

**Skipped.** A PR whose head and body the last marker names, a draft, a closed PR, a PR into any branch but the default, and a PR by an author the repo's `trust.review` does not let in (`dispatch/trust.mjs`), `OWNER`, `MEMBER` and `COLLABORATOR` by default. Dependabot's PRs are read by the Dependabot list whatever it says. The receiver queues the review for every PR, and the task judges the author, so a PR it skips this way still gets its `neutral` check.

**Dependabot.** A PR `dependabot[bot]` opened is held to tests 7 and 8 alone, with no model run, using `review.dependabot` in place of the human-only list. It passes when every changed file is on that list and modified, and every commit's author is `dependabot[bot]` and was committed and signed by GitHub. Anything else waits for a person. A pass merges, or with `merge` false waits for the owner. A conflict posts nothing: Dependabot rebases its own PRs.

**Limits.** A review of every open PR starts no review past five minutes into the turn. Each PR it did not reach goes through the review's usual skips, then gets a `failure` `governor` check saying the turn ran out of time, and is reviewed on its next push or edit. Those checks stop twelve minutes into the turn, inside the task's deadline; the PRs left past that are logged and get no check until their next push or edit. A model run refused by the login's session limit is `limited`, not a failure. A failed review (a merge GitHub refused, an answer outside the schema) exits 1.

**Transcripts.** With `DropBoxUrl` set and the writer saved, each review's transcript is redacted, gzipped and PUT to `<DropBoxUrl>/<date>/pr-review-<PR>-<session>.jsonl.gz` (`dispatch-review-transcript`).

**Spend.** Each review's `dispatch-review` line carries `usage`, what its model run spent as the CLI's result line reports it: `inputTokens`, `outputTokens`, `cacheReadTokens`, `cacheCreationTokens` and `costUsd`. A failed or `limited` run logs what its result line carried. A field the line lacks is left out, and a review with no model run, or whose run printed no result line, has no `usage`.

## Ticket reviews

A repo whose file turns `ticketReviews` on lists its reviews in `ticketReviews`, each with a `name` and a selector, `when` ([constraints/dispatcher-review.md](constraints/dispatcher-review.md)). An issue opened, reopened, or with its body edited queues one `ticketReview` fire naming it. A title-only edit queues none, and nor does a body edit a bot made: governor edits bodies itself, when it takes a session link off a ticket or rewrites a relative wait line, and those edits must not spend a round. Sessions edit as the owner's account, so their edits run the review.

The turn (`dispatch/ticket-review.mjs`) reads the issue and reviews nothing for a closed issue, a pull request, the heartbeat issue or the wait ticket. It reviews only a ticket whose author the repo's `trust.review` lets in, `OWNER`, `MEMBER` and `COLLABORATOR` by default. The receiver queues the fire whoever opened the issue, and the task judges the author. Then, in file order, it runs each review whose selector the ticket meets now and whose newest marker on the thread does not carry the ticket's current key, a sha256 of its body, or, for a review with `types`, of its body and the labels it carries that the entries name, lower-cased and sorted, so a ticket whose type changed is reviewed again at its next body edit or reopening. A label change alone queues no review:

- `when.on`: the event. Only `"opened"` is built, which covers the opening, a reopening and a body edit.
- `when.labels`: labels the ticket must carry, every one. Default none.
- `when.exclude`: labels that keep the ticket out, any one. Default none.
- `when.by`: who may have opened it, as `author_association` values. Default `OWNER`, `MEMBER` and `COLLABORATOR`. A missing association reads as `NONE`.

Each run is one `claude -p` under the stored login with no tools. Governor's fixed frame and then the review's checklist replace Claude Code's system prompt (`--system-prompt-file`), and the answer is held to a schema: a conclusion and its text. On stdin the model reads the ticket's title, labels and body; the title and body of its sub-issue parent and of each same-repo issue its body links; the numbers and titles of the repo's open issues; and which round of this review this is, one more than the review's own markers on the thread. A link to another repo's issue, an issue that does not exist, and a pull request are skipped, logged on `dispatch-ticket-review-link` at info. At most 10 linked issues are read, each body cut at 6,000 characters, and at most 300 open issues listed; stdin says what it left out.

The review's checklist is its `checklist`, text or `{ "file": "<path>" }` read from the default branch with the config file, or governor's default where it sets none. Then come the checklists of the review's `types` entries the ticket matches, in file order. An entry matches a ticket carrying any of its `labels`, in any case. A ticket that matches no entry gets the base checklist alone, and is not failed for lacking a type label. An entry adds to the base and cannot drop it.

The default checklist checks that the ticket states the problem and who has it, says what done looks like, fits its parent and builds none of its non-goals, and repeats no open issue. A ticket that builds a non-goal is `neutral` even if it is also incomplete. A claim about the code is judged as written. From round 3 it concludes `neutral` rather than ask for another edit.

| Conclusion | Comment |
|---|---|
| `success` | `<Name> review: passes. <reason>` |
| `failure` | `<Name> review: waits for an edit. <gaps>` |
| `neutral` | `<Name> review: waits for a person. <reason or gaps>` |

Each run posts a new comment, ending `<!-- governor:ticket-review <name> <conclusion> <key> -->`. Only a comment governor's App posted is read as a review's. The comment is an ordinary comment: the filer session hears it as it hears any comment on its issue, and a person gets GitHub's notification.

**Labels.** A review's `conclusions` names the labels each conclusion adds: `success`, `failure` and `neutral`, each a list, each empty when unset. A `types` entry's `conclusions` names only the conclusions it overrides: for each conclusion, the labels come from the first matching entry that names it, and otherwise from the review's. Before its comment, a run removes each label the other two conclusions name, in the review's `conclusions` or any entry's, that the ticket carries, leaving every label its own conclusion names anywhere. So a `success` on an enhancement never takes off `mode: afk` that a bug entry's `success` adds, and a `failure` takes it off a ticket whose type changed since. Then the run adds each of its own conclusion's labels the ticket lacks, creating a label the repo lacks as the claim label is. So a ticket that fails and then passes after an edit carries the `success` labels and none of the `failure` labels. Governor touches no other label, and reads no other part of the config to decide. The code applies the labels from the conclusion; the model applies none. Governor logs what it changed on `dispatch-ticket-review-labels` at info.

The config is invalid where one label appears under two conclusions of one review, where one label appears in the conclusions of two reviews, where a review whose `by` reaches beyond `trust.auto` names a ready label in any conclusion, or where a conclusion names a label a `types` entry matches on, since applying it would change the ticket's type. It is also invalid where a conclusion names a label the same review's `when.labels` or `when.exclude` names, since a `failure` label the review excludes would stop it reading the filer's fix, or names `labels.claim`, since a run would take the claim off a ticket being built. Each rule reads a review's `conclusions` with every entry's. The ready-label rule reads a review's `by` narrowed by `trust.review`, the authors the review can read. That rule closes a path from a stranger's text to a session: the stranger writes an issue to persuade the review, the review adds the ready labels, and pickup counts labels governor's App adds. Governor's own config read refuses each of these, so it holds whether or not the repo runs the config check.

**Connecting a review to pickup.** Reviews and pickup share no code. They meet only through labels the repo's config names. Two patterns:

- **Review every ticket before it is built.** List the review's `success` label among `labels.ready`. Pickup takes a ticket only when it carries every ready label, so a ticket is not ready until the review has passed it, and a later `failure` or `neutral` takes the label off again. A ticket the review readies is taken at the repo's next pickup sweep (`pickup.sweepHours`): the receiver queues no selection fire for a label a bot adds, and the review queues no pickup fire.
- **Trust a ticket someone has readied.** List the ready labels in the review's `when.exclude`. A ticket that carries them when it opens is not reviewed, and pickup starts it as today. That review's `conclusions` then cannot name those labels, so it readies nothing itself.

A person overrules a review by adding its `success` label by hand. Put the `neutral` labels in `labels.exclude`, so pickup never takes a ticket the review doubted.

**Failures.** A run that fails or answers outside the schema, a label write GitHub refuses, and a comment GitHub refuses, post no marker and log `dispatch-ticket-review` at error. A refused label write posts no comment, so a ticket never keeps a ready label from an earlier `success` under a later `failure` with nobody told. The turn's other reviews still run, and the turn exits 1. A run the login's session limit stops is `limited`: it does not alarm, and no later review in the turn runs. The weekly limit is a fault. With no marker, the ticket is reviewed again at its next edit.

**The loop guard.** A review that concludes `failure` five times in a row on one ticket stops there. After the fifth, governor posts one more comment, `<Name> review: stopped on this ticket after 5 failures in a row.`, saying a person decides what happens to the ticket. It ends in `<!-- governor:ticket-review-loop <name> -->`, and governor logs `dispatch-ticket-review-loop` at error. While that comment stands, later edits do not run that review, which logs `dispatch-ticket-review` at info as skipped; other reviews on the ticket still run. A `success` or `neutral` starts the count again. To let the review run again, delete the guard's comment. The failures before it stay on the thread, so the guard comes back only at the tenth failure in a row, giving the review five more rounds. Only a comment governor's App posted, ending in the marker, stops a review. A guard comment GitHub refuses leaves the review's own comment standing and makes the turn exit 1; with no guard on the thread, the review runs at the next edit, and the guard comes again only at the tenth failure in a row. The limit of five is a constant, above the default checklist's switch to `neutral` at round 3, so a working checklist never reaches it.

**Logs and transcripts.** Each review logs `dispatch-ticket-review` with the repo, the issue, the review's name, its conclusion, its round and `usage`. With `DropBoxUrl` set, each run's transcript goes to `<DropBoxUrl>/<date>/ticket-review-<name>-<issue>-<session>.jsonl.gz`.

## Prompts

A repo's `prompts` map replaces the instruction in a kind of message, or the opening prompt of a kind of session. Governor still writes the facts itself: what happened, the PR or issue, the run and commit, and the standing line. A prompt may name its kind's facts as `{fact}`. A kind the file leaves out gets the default in `dispatch/prompts.mjs`, which names no repo's skill or file.

| Key | Replaces | Facts |
|---|---|---|
| `pickup` | A pickup session's opening prompt, below `Pickup #N 'title'` | `{issue}`, `{repo}`, `{claim}` |
| `signOff` | The standing line's ask to sign off | |
| `unblockedReady` | A ready ticket's ask, below its pickup prompt and the facts of its blocker's close | |
| `unblockedSpec` | A not-ready ticket's spec session's ask, below the facts of its blocker's close | `{issue}`, `{ready}`, `{claim}` |
| `unblockedOwnerSpec` | The ask to a not-ready ticket's owner, the session its body names, below the facts of its blocker's close | `{issue}`, `{ready}`, `{claim}` |
| `waitEndedSpec` | A not-ready ticket's spec session's ask, below the facts of its ended wait | `{issue}`, `{ready}`, `{claim}` |
| `waitEndedOwnerSpec` | The ask to a not-ready ticket's owner, below the facts of its ended wait | `{issue}`, `{ready}`, `{claim}` |
| `unblockedClaimed` | A claimed ticket's session's ask, below the facts of its blocker's close | `{issue}` |
| `unblockedNotPlanned` | The ask in the comment, and message, when a ticket's blocker closed as not planned | |
| `redScheduledRun` | A red scheduled run's session prompt, below the run | |
| `ciBreaker` | A red CI run's ask to its one suspect's session | `{pr}` |
| `ciTriage` | A red CI run's fresh session over several suspects | |
| `ciBumpTriage` | A red CI run's fresh session over a Dependabot bump | `{pr}` |
| `prodTriage` | A failed `triage` target's fresh session | |
| `deployGreen`, `deployGreenMany` | A green deploy's ask, for one PR or several | `{pr}` (the newest), `{target}` |
| `deployRed`, `deployRedMany` | A red deploy's ask, for one PR or several | `{pr}` (the newest) |
| `subscribed` | A CI or deploy notice's ask to a subscriber | |
| `conflicts` | A conflicted PR's ask, to its session or the fallback's | `{base}` |

A value is the text, or `{ "file": "<path>" }`, read from the default branch beside the config file. A skill file's frontmatter is dropped. An unknown key, a fact the kind lacks, or a missing or empty file makes the config invalid.

## Periodics

A periodic is a recurring session a repo lists in its config file, with a name, a prompt and a day limit in whole days (`dispatch/periodics.mjs`). It may add counts of merges into the default branch, issues opened and issues closed, and a minimum gap in hours. The bare hourly fire starts one on its day limit or its counts; an event it counts can start one too.

- **When it is due.** Governor keeps each periodic's record in the state table, under `periodic#<repo>` / `<name>`: the time of its last fire, and the session it started, or none for an unconfirmed launch. A periodic is due once its day limit has passed since that time, or will within half an hour, half the schedule's interval: the record holds the launch's time, a little after the sweep read it, so the sweep nearest the limit fires it rather than every run slipping a sweep. A grace of a whole hour could fire it at the sweep before the limit, whenever that sweep's turn ran later than the last launch, and the runs would creep earlier. One with counts is also due once any count since that time reaches its number.
- **Counting.** Governor keeps no running total. When a counted event arrives, governor reads that kind's count since each periodic's last fire afresh from GitHub, so a lost webhook only delays a fire to the next event or sweep. Merges are pull requests closed into the default branch, counted by merge time, never by comparing commits: a compare stops at 250 commits, and a busy week passes that. Issues opened and closed are counted by when they were opened or closed, pull requests left out. An issue counts, and appears in the prompt's list, only where the repo's `trust.auto` lets its author in, `OWNER`, `MEMBER` and `COLLABORATOR` by default; a bot's issue never does. A merge counts whoever opened its PR. The sweep reads every count it keeps.
- **The fire's time.** A periodic with counts is recorded as of the moment its counts were read, not its launch, so a merge or issue that lands in between is in the next window. One with only a day limit records its launch's time.
- **The carrying turn.** The receiver reads no config file, so it marks every merge into the default branch, issue opened and issue closed in a listed repo as `counted` on a fire. A merge rides its `conflicts` fire, and a close rides the fire that queues what it blocked. An issue opened rides its summons, if it is one, and otherwise queues a `periodics` fire of its own. After the turn's own work, the turn checks the periodics that count that kind, under the `periodics` switch, whatever switch its own work needed; a turn refused for its own switch still checks them. A periodic starts no later than seven minutes into the turn (`EVENT_PERIODIC_WINDOW_MS`), so its launch ends inside the task's deadline; one left unstarted stays due. If the turn's own launch in the repo started nothing, its periodics wait too, since their launch would fail the same way. A record or count that cannot be read there fails the turn, and the sign-off sweep still runs.
- **Nothing to do.** At its day limit, a periodic with counts whose counts counted nothing starts no session. Governor records "nothing to do" as its fire, so its next day limit counts from then. A periodic with only a day limit always starts a session.
- **The minimum gap.** A periodic never fires inside `gapHours` of its last run. A count reached inside the gap fires on the first event or sweep after it. A baseline ran nothing, so it opens no gap; a "nothing to do" record keeps the time of the run before it, and the gap runs from that.
- **The hold.** A periodic never overlaps itself. When one comes due, by count or by day limit, and the session its last fire started is still open, governor starts nothing and logs `dispatch-periodic` with outcome `held`, naming that session. It writes nothing, so the last fire's time stays put, the count keeps growing from it, and the first check after the run ends fires the periodic over the whole window. A day limit whose counts counted nothing is held the same way, since its "nothing to do" record would name no session and the next count would start a second run over the open one. Governor reads the session's own record over the sessions API, under the login's token, refreshed first if it has expired. The sign-off sweep only reads idle, unarchived sessions, so the hold does not wait for it to report. A run is finished once its session is archived, by the sweep or by hand, signed off or not, or once the API no longer has it. A record with no session, from an unconfirmed launch, is a finished run. A session that cannot be read, or whose record carries no status, refuses the periodic for the turn (`dispatch-periodic-unread`, and the turn exits 1); it is never taken for a finished run.
- **No record.** A new periodic, or one whose record was lost, has none. The fire writes now as the baseline and starts nothing, so the first run comes one day limit later. The baseline also writes the periodic's heartbeat line where it has none ([The heartbeat](#the-heartbeat)). A lost record costs at most one late run, never a burst of runs.
- **The launch.** Due periodics go into the fire's launch plan ahead of the tickets, the one that came due first going first. They do not count against `DispatchCap`, but a cap of 0 still starts nothing. A cap of 0 logs one `dispatch-periodic` line per repo with outcome `not started`, the cap as its reason and the due periodics listed oldest due first, whether the check ran on the bare fire or on an event, and leaves their records, so each stays due. They share the fire's seven-minute launch window, and one left unlaunched stays due for the next fire.
- **The session.** It is named after the periodic, in the repo's environment. Its prompt is the periodic's, then a line governor writes: `This periodic last fired at <time>.`, `This is the first run of this periodic that governor has a record of.` after a baseline, or that its last day limit found nothing to do. For a periodic with counts, governor then lists what each count counted since that time, each item by number and title, up to a hundred of each kind. No repo can drop or reword these lines.
- **Connectors.** A periodic may list `connectors`, the claude.ai connectors its session needs, by their names in the account's connector list. The CLI's create request has no field for connectors, so a session `claude --cloud` starts has none of them. Such a periodic starts as a run of a routine instead (`dispatch/routines.mjs`), under the login's token. Governor turns each name into the connector's uuid and URL from the account's list (`GET /v1/mcp_servers`). A row names its connector by `display_name` and carries a tagged `id`, which governor turns into the uuid a routine takes as the CLI does: an id starting `mcprs` reads as `mcpsrv`, and past `mcpsrv_` and two more characters the rest is a base58 number, written as 32 hex digits in a uuid's 8-4-4-4-12 groups. A row lacking its `id`, `display_name` or `url`, or whose `id` gives no uuid, refuses the fire and says what the row lacks. It keeps one routine per periodic, found by its name, `governor <owner>/<repo>: <periodic>`, and creates it on the first fire. It reads the routines list (`GET /v1/code/triggers`) a page at a time, asking for the next with `cursor=<next_cursor>` while the answer says `has_more`, until the routine turns up or the list ends. It reads at most ten pages. A list with more past them, or one with more that names no cursor, refuses the fire rather than create a second routine beside one on a page not read. Before each fire it updates the routine with this fire's prompt and governor's lines, the repo's environment and source, the model, and the named connectors and no others, and sets the routine disabled, on a cron that fires once a year (midnight on 1 January). The routines API refuses a cron with no firing time or one less than an hour apart, and a disabled routine never starts a run from its own schedule, but still runs when fired. If someone switches it on by hand, it runs once a year, not beside governor's fires. It then fires it (`POST /v1/code/triggers/<id>/run`). The run's session is the one the fire answers with, or the routine's first run session not listed before the fire (`GET /v1/code/sessions?trigger_id=<id>`), read up to six times five seconds apart. That session is recorded and held like a launched one. A fire whose session governor cannot find is an unconfirmed launch. So is a fire that times out, fails on the network, or answers a 5xx, 408 or 429: the server may have queued the run. A fire answered with any other 4xx, or one that throws before its request is sent, started nothing, and no run session is read for it: a 409's earlier run would otherwise be taken for this fire's. These request and answer shapes come from the bundled CLI, not a published API, so each call logs `dispatch-routine-answer` at info: the repo, the periodic, the call, the routine, and the answer's keys and their types, any routine or session id in it, and for a list its row count, `has_more` and its first row's keys. No other text the API answers is logged, since it carries the periodic's prompt and its sessions' titles. A call that fails logs `failed: true` and the HTTP status it was answered with. A connector the account has not connected starts nothing: governor logs `dispatch-connector-missing`, naming the repo, the periodic and the connector, writes no record, and goes on with the repo's other launches, so the next fire tries again. Any other refusal, such as a 400 on the create, a routines list that runs past ten pages or a 403 on the fire, is handled the same way under `dispatch-routine-refused`, which says what the API answered. The CLI is not at fault there, so the repo's tickets and its other periodics still start.
- **The record.** A launch that started, or may have, writes the new record, and only over the record the fire read, so two turns never both record one fire. The write comes after the launch, so it is the one task at a time that keeps two turns from both starting a periodic. A failed launch writes nothing and the periodic stays due. A failed `claude --cloud` launch also leaves the rest of its repo for the next fire (`dispatch-repo-skipped`), as after a ticket's failed launch. A routine the routines API refused stops only its own periodic ([Connectors](#periodics)).
- **A failed read.** A record or a count that cannot be read refuses that periodic for the turn, and is never taken for a missing record or an empty count. The turn logs `dispatch-periodic-unread` and exits 1. A record that could not be written after a launch logs `dispatch-periodic-unrecorded` and exits 1, since the next fire may start the periodic again.

## Hooks

A hook is a session an outside system starts with a signed request ([Hooks](hooks.md), `dispatch/hooks.mjs`). The receiver checks the signature and queues a `hook` fire. The task checks the file lists the hook at that key version, then decides whether the fire starts a session or goes into one.

- **The record.** Governor keeps each hook's last session in the state table, under `hook#<repo>` / `<name>`: the session its last launch started, and when. The receiver cannot reach that table.
- **An open session.** When the record names a session that is neither archived nor gone, the fire goes into it as a message. The message starts with a relay line that names the hook rather than GitHub. It says which hook fired again and when, quotes the caller's text line by line as the caller's data, and ends with the session's standing line, like every other message. It does not repeat the hook's prompt, which the session already has. Nothing starts, and the record stays. Governor reads the session's state the way the periodics' hold does: its own record over the sessions API, under the login's token, refreshed first if it has expired.
- **A closed session, or none.** When the session is archived, by the sign-off sweep or by hand, or the API no longer has it, or there is no record, the fire starts a new session on the hook's prompt, named after the hook, in the repo's environment. A session archived between the read and the send refuses the message, and the fire starts a new one the same way. A send that fails any other way starts nothing, since the session may be live, and the turn exits 1.
- **Writing the record.** A launch that printed a session writes the record naming it, only over the record the turn read, so two turns never both record a session for one hook. Another record standing, or a write that fails, logs `dispatch-hook-unrecorded` at error and the turn exits 1, since the next fire may start a second session.
- **A failed read.** A record, or a session's state, that cannot be read refuses the fire, and the turn exits 1. It is never taken for a missing record or a closed session.
- **Out of time.** A send that was refused only after the launch window had passed starts nothing, since a launch then might outrun the deadline. A fire is not tried again, so the turn logs `dispatch-hook-unstarted` at error and exits 1.
- **A lost record.** With no record, the next fire starts one session and records it. The fires after it go into that session, so a lost record costs at most one extra session, never a burst.
- **Two hooks.** Each hook has its own record, so a fire for one hook never messages another hook's session.

## The heartbeat

A repo turns the heartbeat on and names one issue, `"heartbeat": { "issue": <number> }`, so a check outside governor can read when each thing governor runs for it last ran and how it ended (`dispatch/heartbeat.mjs`). The issue's body must already carry `<!-- governor:heartbeat -->`. Governor keeps its own block under that marker, ended by `<!-- governor:heartbeat-end -->`, and changes nothing else in the body:

```
<!-- governor:heartbeat -->
- pickup: last sweep 2026-10-29T20:00:00.000Z, started 2 sessions
- periodic "Code review": last fire 2026-10-29T18:04:11.000Z, by 20 merges, session https://claude.ai/code/session_…, open
- periodic "Weekly retro": last fire 2026-10-27T20:00:00.000Z, by its day limit of 7 days, session none, nothing to do
- periodic "Backlog review": first read 2026-10-29T20:00:00.000Z, session none, not fired yet
<!-- governor:heartbeat-end -->
```

- **Pickup's line** gives the last sweep's time and how many ticket sessions it started. Only the bare hourly fire writes it, on a fire that swept the repo at its interval, in a repo whose file turns pickup on, whose backlog it read, and where not every claim or launch failed. A label or a close never freshens it.
- **A periodic's line** gives its last fire's time, which limit fired it (its day limit, or the count that reached its number), the session, and its state: `open`, `signed off`, `held while that session is open`, `nothing to do`, or `not fired yet`. Its own fire writes it, on the hourly fire or on the event that brought it due. A held fire leaves the time at the open run's start and names that session. A failed launch leaves the line where it was.
- **A periodic governor has not fired yet.** Its line appears when governor first reads it and writes its baseline, on the sweep or on a counted event's turn. The line gives the baseline's time, `session none`, and `not fired yet`. Each sweep sends it again until the first fire, so a write that failed is made good two hours later. A baseline only adds a missing line. After a lost record, the line keeps its last real fire, so the checker still reports the late run. The periodic's first fire replaces the line.
- **Signed off.** When the sign-off sweep, on any turn, archives the session an open or held line names, it marks that line `signed off`. It never moves the line's fire time.
- **A wrong issue.** A body without the marker gets no write, and `dispatch-heartbeat-refused` names the repo and issue. A read or write that fails logs `dispatch-heartbeat-unwritten` and the turn exits 1.

A file in the older shape, `"heartbeat": { "issue": <number>, "marker": "<!-- … -->" }`, keeps what it had: the hourly sweep adds or updates one `last-run: <time>` line under the repo's own marker, after a sweep in which not every claim or launch failed. Nothing writes a line per periodic there.

## The webhook

GitHub posts every installation's events to one Lambda Function URL (`governor-webhook`) through the App's own webhook. The events are those in `HOOK_EVENTS` (`dispatch/webhook/route.mjs`). A delivery whose signature matches the stack's key (`governor/webhook-secret`) is routed from its payload alone: the receiver holds no GitHub token and reads no config file.

- A repo whose owner is not on `DispatchOwners` queues nothing: `200`, and `webhook-ignored` at info. An outsider who installs the public App can page nobody.
- Every fire names the repo its delivery came from. The task reads that repo's file and refuses a fire its switches do not turn on.
- A refused fire still costs a whole task, so the receiver drops a fire whose switch is off before it reaches the lane. It reads no file. Each time the task reads a served repo's file, it writes every switch, as the turn reads it, to the repo's item in the hook table, in the same write as the hooks (below), and before it refuses its own fire. A delivery that would queue a fire reads that item once (`droppedBy`, `dispatch/webhook/switches.mjs`). Three kinds of fire are handled apart. A red run on the default branch is dropped only when `ciMessages` and `deployMessages` are both off, since the receiver cannot tell CI from a deploy. A red run naming no workflow file is never CI to the task, so it is dropped when `deployMessages` is off. A fire carrying `counted` is kept wherever `periodics` is on. A merge's `conflicts` fire is never dropped: its turn reads the file the merge may have changed and writes the item, so a switch just turned on stops being dropped once that turn has run. A missing item, one written before it held switches, and a read that fails all queue every fire, and the task decides. A failed read logs `webhook-switches-unread` at error and never answers `503`, since GitHub does not redeliver a failed delivery by itself. A delivery whose fires are all dropped answers `200` with a reason naming the switch. Fewer refused turns also means fewer sign-off sweeps, so a signed-off session in a busy repo may wait a little longer to be archived.
- Workflow and merge events are routed by the default branch the payload names, never by `main`.
- A label a person adds queues a selection fire only if it is one of the repo's ready labels. The task writes them, `labels.ready` as the file reads, to the repo's item in the hook table, in the same write as the switches, and the receiver reads them in the same one read. A label the item does not list is dropped, and the delivery's reason says it is not one of the repo's ready labels. A missing item, one written before it held ready labels, a malformed item and a failed read queue the fire, and the task decides. A new ready label reaches the item at the repo's next turn, which a merged pull request queues; until then a ticket given it waits for the sweep. No deploy is needed.
- A label added by a bot queues no selection, since governor's own claim and release are a bot's. Subscribers still hear it.
- A message reaches a session only from an author the repo's `trust.relay` lets in ([Whose text reaches a session](#who-a-pr-or-issue-belongs-to)). The task writes `trust.relay` as governor reads it to the repo's item in the hook table, in the same write as the switches, and the receiver reads it in the same one read. The receiver drops a message only where its author, or the author of the body that named the session, is outside `OWNER`, `MEMBER` and `COLLABORATOR` and the item's list: that refusal is silent. A missing item, one written before it held `trust`, and a read that fails all judge by the default list, so a stranger's comment is still dropped and an owner's still queued. Each message fire names the associations it was judged by, and the task refuses one the file's `trust.relay` does not let in, at info, before it sends. The receiver routes a delivery under every value first, and reads the item only where that queues a fire.
- A delivery's id is its deduplication id on the queue, so a redelivery is not a second fire.

A request on a `/hooks/<owner>/<repo>/<hook>` path is a hook's, not GitHub's ([Hooks](hooks.md)). The receiver derives the hook's key from `governor/hook-secret`, the repo, the hook and the version the `Governor-Signature` header names, and checks the signature in constant time. It reads no config file. What it knows of the repo's hooks is the repo's item in its own table, `DispatchHookTable` (`dispatch/webhook/hook-table.mjs`): each hook's name, `keyVersion` and `perHour`, as the task last read the file. The task writes the item each time it reads a served repo's file, with an empty list when the file turns `hooks` off or lists none. A write that fails logs `hook-table-unwritten` at error. A repo that stops being served keeps its last item. After the signature, the clock and the owner check, the receiver reads the item. A hook it does not list is refused, and so is a key version older than the item's. A repo with no item yet is queued. The task still checks every fire against the file (`dispatch/hooks.mjs`), so a fire queued before the item changed, or after an item was lost, is still refused. Last, the receiver counts the fire against the hook's cap: one item per hook and clock hour in the same table, raised by one conditional `UpdateItem` only while the count is under the hook's `perHour`, or 20 for a repo with no item yet, and expired when the hour ends. The item also holds each signature it counted, and the same update adds the signature only when the hour has not counted it. So a request resent in the hour that counted it takes no place: it is queued again, where the queue drops it if the first send got through inside its five-minute deduplication window, and a retry after a `502` still reaches the queue. A `perHour` is at most 100, which keeps the item under 7 KB, so a count or a `429` costs at most 7 write units. Only a request that passed every check before it is counted, so a request with a bad signature, a stale key or no text takes no place in the hour. A fire past the cap is refused, so a leaked key can put at most one hour's cap on the queue every repo shares. The receiver holds `GetItem` and `UpdateItem` on this table and nothing on the state table, since it faces the internet and the state table holds records the PR review trusts. A hook fire's deduplication id is its signature, so a replay inside the queue's five-minute window is not a second fire. The two clock limits add up to 4 minutes 40 seconds, 20 seconds under that window, which is the receiver's timeout. The window runs from the first send, not from the clock check, and between the two the receiver calls `GetItem` and `UpdateItem` on the hook table and then `SendMessage`, each of which the SDK may retry. Nothing reaches the queue once the receiver stops, so a replay accepted at the end of its validity still reaches the queue inside the window. A test reads the receiver's `Timeout` from the stack and fails if the margin is shorter. So a request is valid for no longer than the queue remembers it, and every replay of one is dropped. No line logs a signature or a key.

### The fire lane

Every fire, the schedule's included, goes on `governor-fires.fifo`, a FIFO queue with one message group. [This animated diagram](https://t-d-d.github.io/gh-governor/fire-lane.html) walks through one fire, a burst, the exit gap, a failed start and requests the receiver refuses.

- **The task takes the fires.** The dispatcher task is the lane's only reader (`dispatch/lane.mjs`). It long-polls the lane, takes the head fire, deletes it, logs `fire-taken` with the fire's message id and kind, and runs the fire as its own turn. It repeats until the lane has been empty for a minute since its last turn, then exits. So a burst pays one cold start, not one per fire. Each turn restores the login from the secret and stores any refresh back before the next fire, and the task clears what the CLI left under its home and working directories between fires. A task stops taking fires after 30 minutes and leaves the rest to a fresh one, so a long burst does not keep running the image it started with after a deploy.
- **Each turn has its own deadline.** Eighteen minutes, counted from the turn's start. A turn that runs past it logs `dispatch-failed` with the reason `deadline`, and the task exits. A turn that threw but was still waiting for a session record to be written when the deadline came puts the error it threw, with its stack, on that line. The fires behind it were never received, so they wait on the lane for the next task. A turn that fails is logged and not retried. A fire the task's parser refuses goes to `governor-fires-dead.fifo` at once, as it came, with the reason on the message.
- **The starter only starts tasks.** The starter (`governor-starter`, `dispatch/webhook/starter.mjs`) holds no fire. Each call asks whether a fire waits on the lane and whether a dispatcher task is running, and calls RunTask only when a fire waits and none runs. It runs one call at a time, so two calls never both start a task. ECS can take a few seconds to list a task it has just started, so the starter also counts the task it last started as running, until that task's stop event arrives or two minutes pass. It logs `task-started` with the task and what called it.
- **Three things call the starter.** The receiver, after it queues a request's fires: a call that fails logs `starter-poke-failed` at error, and the delivery still answers `202`. Every task's stop event, through `governor-not-run` and `governor-task-stopped`, so a fire that lands while a task is exiting finds the next task started. And `governor-starter-backstop`, every minute, which catches a call that never came and a fire queued with no call. A turn that queues fires, and a fire queued by hand, call nobody: the running task takes them, or the backstop starts a task within a minute.
- **A failed start loses nothing.** A task that fails to start (an image pull refused, no placement) never took a fire, so the fire is still on the lane. Its stop starts the next attempt, which rides on the task's `startedBy`, up to three in a row. Past that the starter logs `start-gave-up`, which pages `governor-start-gave-up`, and the next call from the receiver or the backstop begins a new chain.
- **A fire that is never deleted.** The lane hides a received fire for 30 seconds, and dead-letters one received five times without a delete: a fire whose task dies every time between the two. `governor-fires-dead` pages on anything in the dead-letter queue. `governor-lane-stalled` pages when a fire has waited 45 minutes, however the lane stalled.

After every apply, the deploy runs `scripts/point-app-webhook.mjs`, which writes the receiver's URL and the stack's key to the App's webhook config, as the App. It first reads the App's events, and writes nothing while one the receiver routes is unticked. The deploy's conformance checks (`scripts/conformance.mjs`) then read back the App's events and post once, unsigned, to the receiver, failing on anything but its own `401`. They post once more, unsigned, to a hook path (`hook-url`), and fail on anything but `401`.

The App's **Advanced → Recent Deliveries** shows each answer:

| Answer | Meaning |
|---|---|
| `202` | A fire was queued. |
| `200` | Nothing was queued; the body says why (an unlisted owner, a stranger's mention, a bot, a session's own post, or a switch the repo's file turns off). |
| `401` | The signature does not match the stack's key. |
| `403` with no receiver log line | AWS refused the URL before the receiver ran. The stack grants both `lambda:InvokeFunctionUrl` and `lambda:InvokeFunction`. |
| `502` | The receiver threw, or the queue refused the fire. Redeliver retries it. |

A hook request's answers, which only its caller sees:

| Answer | Meaning |
|---|---|
| `202` | A `hook` fire was queued, naming the repo, the hook, the key version and the text. |
| `200` | The repo's owner is not on `DispatchOwners`: `hook-ignored` at info, nothing queued. |
| `400` | The body is not JSON, or holds no string `text`: `hook-refused`, nothing queued. |
| `401` | The header is missing or malformed, the signature does not match, or `t` is more than 30 seconds ahead of the receiver's clock or more than 4 minutes 10 seconds behind it: `hook-refused`, nothing queued. |
| `401` | The hook table's item for the repo does not list the hook: `hook-refused` at warn, nothing queued. |
| `401` | The key version is older than the one the item names: `hook-key-stale` at error, which pages `governor-hook-key-stale`, nothing queued. |
| `404` | A path under `/hooks/` that names no repo and hook. |
| `413` | The text is over 32 KiB, or the fire would not fit a lane message: `hook-refused`, nothing queued. |
| `429` | The hook has had its `perHour` fires this clock hour: `hook-refused` at warn, nothing queued. |
| `503` | The hook table's item could not be read: `hook-table-unread` at error, nothing queued, so the caller sends it again. A failed read is never taken for a missing item. |
| `503` | The hook's count for the hour could not be raised: `hook-table-uncounted` at error, nothing queued, so the caller sends it again. |

## Invoking by hand

```bash
node scripts/run-turn.mjs --kind probe                                     # check the runtime; exits with what it proved
node scripts/run-turn.mjs --kind schedule                                  # a sweep of every served repo whose interval has passed, now
node scripts/run-turn.mjs --kind schedule --repo owner/name                # one repo's pickup and sweep
node scripts/run-turn.mjs --kind dispatch --repo owner/name --prompt '…' --session-name '…'   # one session, no ticket
node scripts/run-turn.mjs --kind message --repo owner/name --session <session_… or URL> --text '…'  # text into a session
```

Every kind but `probe` and a bare `schedule` needs `--repo`: nothing falls back to a default repo. It needs the AWS CLI as an identity that may run the task and send to the queue.

A probe starts its own task, since it touches no login. It waits for the task to stop, prints its log and exits with its exit code. Every other kind queues on the fire queue and waits behind whatever is ahead of it. The running task takes it, or the starter's backstop starts a task for it within a minute. The script finds its turn by the task's `fire-taken` line for its message in `/governor`, waits for the turn's result line, prints the task's log from the one to the other, and exits with the turn's exit code. `--no-wait` returns at once. Start a task any other way only when `aws ecs list-tasks --cluster governor` shows none and the queue is empty.

A message needs no pseudo-terminal: the turn runs `claude -p --cloud <session> --output-format json` with the text on stdin, and an archived session refuses it. A message wakes an idle session within seconds.

When governor is down, open a session by hand from the claude.ai app or `claude --cloud`.

## Minting the login

On a laptop or in CloudShell, with `claude` and the AWS CLI signed in as an identity that may write `governor/claude-login`:

```bash
node scripts/mint-claude-login.mjs --profile <p>   # laptop
node scripts/mint-claude-login.mjs                 # CloudShell
```

It first checks that the AWS identity can reach the secret, and stops there if not. Then it starts the sign-in under a throwaway `CLAUDE_CONFIG_DIR`, which also namespaces the macOS keychain item, so the login the machine already holds is never read or written. Pick the subscription option and sign in as the account the sessions will run under. It refuses a setup-token, writes the secret, removes the throwaway directory, and prints the scopes and both expiries.

The secret holds `{ credentials, account }`: the CLI's `.credentials.json` text verbatim, and the account and organisation UUIDs. Not the email address. The turn names the organisation to every CLI call it spawns, so none depends on the CLI's profile fetch.

Never sign that login out: a revoke would kill the stored copy. A refresh rotates both tokens and moves the access expiry, but not the refresh expiry, which is fixed about two weeks after the mint. Past it, the refresh fails and governor stops. So mint again before then. Within three days of it, each turn logs `dispatch-login-expiring` and `governor-login-expiring` pages.

## Alarms

Every alarm publishes to the `governor-alerts` topic, which emails the address in Parameter Store under `/governor/alert-email` once the subscription is confirmed.

| Alarm | Fires on |
|---|---|
| `governor-errors` | A `dispatch-failed` line in `/governor`: a dead login, a GitHub read refused, a launcher that cannot start, every launch failed, the deadline. |
| `governor-stale-runs` | `dispatch-stale-runs`: the runs list still lacked a run, or a cursor could not be read. The next run of the same workflow catches up. |
| `governor-login-expiring` | The stored login is within three days of its refresh expiry. Mint again. |
| `governor-claim-stranded` | A ticket was claimed but no marker names its session. It stays claimed; if no session is working on it, put the ready label back. |
| `governor-session-unrecorded` | Governor started a session and could not record it (`dispatch-session-unrecorded`), so the PR review would let a ticket's mode label waive a human-only path for its PRs. Put the item `session#<session id>` / `started` in the state table, or review that session's PRs yourself. A line with no session URL is a launch that may have started a session but printed none: find it in the sessions list by the line's session name and time. A launch that ran past its budget pages this way at once. If its launcher prints the session later, an info line `dispatch-session-late` names it with the same session name, so you can close that page against it once the item `session#<session id>` / `started` is in the state table. If its turn had already ended by then, nothing waits for the record, so a second page names the session. A line that names a routine (`routine`, `routineName`) is a periodic's routine run: find the session among that routine's run sessions, started shortly before the line's time. |
| `governor-config-invalid` | A served repo's file fails the schema. |
| `governor-repo-skipped` | A repo's `claude --cloud` launch started nothing; its tickets wait for the next fire. |
| `governor-routine-refused` | The routines API refused a periodic's routine, or its fire with a 4xx other than 408 and 429. That periodic waits for the next fire; the repo's tickets and other periodics did not. |
| `governor-hook-key-stale` | A hook fire was signed with a key version the repo's file has moved past (`hook-key-stale`), refused by the task or, once the hook table has the new version, by the receiver. Unless a caller is still to be moved to the new key, treat the old key as leaked. |
| `governor-not-started` | EventBridge could not invoke the receiver on the schedule. |
| `governor-not-run` | Tasks repeatedly failed to start their container. The stop event in `/governor` says why. The fires wait on the lane. |
| `governor-start-gave-up` | Three tasks in a row failed to start, so the starter stopped trying for that chain. The next call from the receiver or the backstop tries again. |
| `governor-not-run-undelivered` | A stop event could not reach the starter or `/governor`. The fire waits on the lane, and the backstop starts its task. |
| `governor-lane-stalled` | A fire has waited 45 minutes on the lane. `/aws/lambda/governor-starter` has `start-failed` lines if tasks are not starting. |
| `governor-fires-dead` | A fire reached the dead-letter queue: the task refused it (`fire-refused` in `/governor`), or it was received five times without a delete. |
| `governor-webhook-errors` | The receiver threw. |

A message an archived session refused, with no fallback tried, is not an error. Neither is a review the login's session limit refused.

## Troubleshooting

**A mention did nothing.** Read the App's Recent Deliveries. `200` carries the reason. `202` queued a fire: the receiver's `webhook-queued` line in `/aws/lambda/governor-webhook` names its message id, and the task's `fire-taken` line for that id in `/governor` opens its turn. No `fire-taken` line means no task took it yet: `/aws/lambda/governor-starter` has `task-started` when a task started, or `start-failed` with why. No delivery at all means the App is not subscribed to that event: tick it in the App's settings.

**A ready ticket was not picked up.** Check that the repo's file turns `pickup` on and lists the ticket's labels as ready, that the ticket has no open blocker, no claim label, no label the file's `exclude` lists and no `Blocked until:` line with a date still to come, and that `trust.task` (or `pickup.by`) lists its author's association. A `dispatch-pickup` warning naming its ready labels means a template, a bot or the author added them, and someone with triage access must add them again. Where the repo narrows `trust.start`, a `dispatch-pickup` line naming `trust.start` means someone it leaves out readied the ticket, and a warning that a lookup failed means the next turn tries again. A ready label new to the file waits for the sweep until the repo's next turn has written it to the hook table. `dispatch-plan` in `/governor` says what the fire planned and why.

**A session was not archived.** Its last reply's last line must start `Signing off`, and the session must be idle. `dispatch-signoff` in `/governor` names each candidate and the decision.

**A task was slow to start.** Every dispatcher task's ECS stop event is in `/governor`, as an `ECS Task State Change` line. Its `detail` carries `createdAt`, `pullStartedAt`, `pullStoppedAt`, `startedAt` and `stoppedAt`: the image pull is `pullStartedAt` to `pullStoppedAt`, and the whole start is `createdAt` to `startedAt`. Find the task's line by its task ARN, which the starter's `task-started` line in `/aws/lambda/governor-starter` names. A task runs many fires, so the start a fire waited for is that of the task whose stream holds its `fire-taken` line. The `governor-not-run` rule writes the stop of a task that failed to start, and the `governor-task-stopped` rule writes every other stop, so the two never write the same event. EventBridge delivers at least once, so now and then a task has two identical lines: read either. ECS itself forgets a stopped task after about an hour, so `aws ecs describe-tasks` answers only for a recent one.

**The deploy's probe is red.** The probe prints the task's log, which says whether the task could not reach the network, hold a pseudo-terminal or find the CLI. A task that never ran its container, such as one whose image pull was refused, has no log, and the probe prints its stop reason instead.

## Pages

This page and the README are Markdown and Mermaid, which GitHub renders in place. A diagram that needs motion or controls is an HTML page instead, and GitHub shows an `.html` file as source. So those pages live in `docs/pages/` and publish with GitHub Pages at <https://t-d-d.github.io/gh-governor/>. This page links to one where a diagram needs it.

- **One file per page.** Each page is a self-contained HTML file, with its CSS and JS inline and no build step. `docs/pages/index.html` lists them, and a new page adds a line there. The public-repo rules apply to a page as to any file. The scan reads a hex colour of four or more digits and no letter as an issue number, so a page writes such a colour as `rgb()`.
- **Publishing.** [.github/workflows/pages.yml](../.github/workflows/pages.yml) runs on a push to main that changes `docs/pages/**` or the workflow. It calls the gate first, so only a green merge publishes, then uploads the folder with GitHub's Pages actions. It has no manual trigger, reads no secret or variable, and is apart from the stack deploy, so a failed stack deploy does not hold up the docs.
- **Previewing from a branch.** Pages serves one site per repo and has no branch previews. A pull request that adds or changes a page links a preview in its description, rendered from the branch by raw.githack.com: `https://raw.githack.com/t-d-d/gh-governor/<branch>/docs/pages/<page>.html`.
